# Task 4: QA, QC or Testing

| | Activity | Answer | Why |
|---|---|---|---|
| (a) | Preparing a coding standard document | **QA** | It is about the process. It is written before coding to prevent defects, and the handout itself gives coding standards as an example of QA. |
| (b) | Running a test of the login page | **Testing** | We execute the software with inputs to find defects. Testing is one of the QC activities. |
| (c) | Reviewing a design document | **QA** | It is a review, which is a preventive activity. A design mistake is caught before it turns into wrong code. The handout puts reviews under QA. |
| (d) | Checking a release build against an acceptance checklist | **QC** | We inspect the actual product (the build) and check if it meets the requirements. It is detective, and no new process is defined. |
| (e) | Training the team on the testing process | **QA** | It improves how the team works (the process), so it is preventive. |

Note on (c): some books call reviews a QC activity because a work product (the design document) is being examined. I followed the handout, which lists code reviews as QA.

# Task 5: Verification or Validation

| | Activity | Answer | Why |
|---|---|---|---|
| (a) | Code walkthrough | **Verification** | The code is read and checked against the design and specification without running it. Are we building the product right? |
| (b) | User acceptance test | **Validation** | The user checks that the system does what they actually need. Are we building the right product? |
| (c) | Reviewing the SRS | **Verification** | A review of a document (static check), done to see that the SRS is complete and consistent. |
| (d) | Running the system with real user data | **Validation** | The software is executed with real data to see if it meets the real needs of the user. |
